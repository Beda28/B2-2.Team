# 팀 협업 가이드

## 1. GitHub Flow 브랜치 전략

- main: 안정적인 기본 브랜치
- feature/\<name\>-\<topic\>: 작업 단위 브랜치

GitHub Flow는 작업을 작은 단위로 분리하고 PR로 검토하기 위해 사용합니다.
변경 이유와 리뷰 이력을 남기며 main을 안정적으로 유지합니다.

## 2. 브랜치 네이밍 규칙

- 개인별로 최신 main에서 feature 브랜치를 만듭니다.
- 각 작업 브랜치는 main에서 독립적으로 분리합니다.
- 변경사항은 PR을 통해 main에 병합합니다.

## 3. 커밋 메시지 컨벤션

- feat: 기능 추가
- fix: 오류 수정
- docs: 문서 변경
- refactor: 동작 변경 없는 코드 정리

변경 대상을 명확하게 작성하며, update, temp, wip처럼 의미 없는 메시지는 사용하지 않습니다.

## 4. Issue 및 PR 작성 규칙

- 작업 전 Issue에 목적과 할 일을 작성하고 PR과 연결합니다.
- PR 본문: What(변경 내용) / Why(변경 이유) / How(구현 및 확인 방법) / Closes #번호
- 병합 전 작성자 외 최소 1명의 승인을 받습니다.

## 5. 코드 리뷰 규칙

- PR마다 변경 파일이나 구체적인 코드를 근거로 실질적인 리뷰 코멘트를 최소 1개 남깁니다.
- 리뷰어와 작성자는 답변이나 수정 내용으로 최소 1회 이상 상호작용을 기록합니다.
- LGTM만 작성하는 리뷰는 하지 않습니다.

## 6. 충돌 발생 시 대응 흐름

1. 충돌 상황을 확인하고 팀원에게 공유합니다.
2. 충돌 파일의 마커(<<<<<<<, =======, >>>>>>>)를 확인합니다.
3. 양쪽 변경사항을 검토하고 팀원과 협의하여 해결합니다.
4. 충돌 마커가 제거되었는지 확인하고 병합 결과를 검증합니다.
5. 해결 과정, 명령어, 결과를 [docs/conflict-resolution.md](conflict-resolution.md)에 기록합니다.
