# 팀 협업 가이드

## 1. GitHub Flow 브랜치 전략

- main: 안정적인 기본 브랜치
- 최신 main에서 작업 브랜치를 만들고, PR 리뷰 후 병합합니다.

## 2. 브랜치 네이밍 규칙

- feature/이름-주제

## 3. 커밋 메시지 컨벤션

- feat: 기능 추가
- fix: 오류 수정
- docs: 문서 변경
- refactor: 동작 변경 없는 코드 정리

## 4. Issue 및 PR 작성 규칙

- 작업 전 Issue에 목적과 할 일을 작성하고 PR과 연결합니다.
- PR 본문: What(변경 내용) / Why(변경 이유) / How(구현 및 확인 방법) / Closes #번호

## 5. 코드 리뷰 규칙

- 병합 전 작성자 외 최소 1명의 승인을 받습니다.
- 실질적인 리뷰 코멘트와 작성자의 답변·수정 내용을 남깁니다.

## 6. 충돌 발생 시 대응 흐름

1. 충돌 내용과 양쪽 변경 의도를 확인하고 팀원과 협의합니다.
2. 충돌을 해결하고 결과를 확인합니다.
3. 해결 내용을 커밋하고 PR에서 공유합니다.
4. 과정, 명령어, 결과를 [충돌 해결 기록](conflict-resolution.md)에 남깁니다.
